## Safe, no-additional-spend operator steps (private authorised workstation only)

1. Confirm the exact project ref **before** touching any database, and retain a rollback plan. Use a machine with an **encrypted disk**, supported PostgreSQL client utilities, enough free disk space and a private, non-synced directory **outside this repository**. Do not run an export from a public CI runner or write database credentials or dumps into a PR, chat, Vercel artefact or GitHub Actions log. Use authorised access to Development; do **not** reset existing credentials just to gain access without separate approval.
2. Put credentials in an OS secret manager and supply them to libpq through a permission-restricted `PGPASSFILE` (mode 0600) or its equivalent. Set `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`, `PGSSLMODE=verify-full` for the exact **Development** direct or session-pooler connection, as supported by the environment. Never place a password in a `--dbname` command argument or your shell history. **Do not paste or print the connection string, dump or credentials.** Use the correct SSL root certificate/trust configuration.
3. Make a fresh, private output directory with `umask 077`. Capture a **consistent complete logical backup**, not only a subset of Colzo tables: use the documented Supabase CLI flow for roles/schema/data (or a reviewed `pg_dump`/`pg_dumpall --no-role-passwords` equivalent). A custom-format archive may be made using `pg_dump --format=custom --file <private-path>/database.dump` with libpq env vars. Verify the archive can be enumerated with `pg_restore --list`. Preserve applicable migration history; inspect any permission failures or excluded managed-schema objects rather than silently treating a partial backup as complete. Verify roles, relevant policies, Auth and Storage metadata, and edge-function config dependencies.
4. Obtain a fresh 32-byte AES key from a **private secret manager** for `COLZO_BACKUP_KEY_HEX` (never committed, printed or passed as a command-line argument). Encrypt each private dump using `node scripts/colzo-backup-integrity.mjs seal <private-input> <private-output.czbak>`, then run `verify` on the encrypted artefact. Keep key and encrypted backups **separate**; maintain a tested key-recovery process. Securely remove disposable plaintext copies only after confirming retained, decryptable encrypted backups. Record SHA-256 checksums and timestamp in a **secret-free** operator record.
5. Restore the real backed-up database to a **separately authorised, isolated destination** with no route to Production or real-customer workspaces. Review the exact destination identity and costs before creating a new hosted project. For a local restore, use a private socket-only PostgreSQL 17 instance with platform-dependent roles/extensions handled explicitly; for a Supabase-to-Supabase restore, follow Supabase's supported procedure and preserve required Vault/pgsodium keys securely. **Never** point `pg_restore` or destructive `supabase db reset` at the existing Development or Production project. Restoration must use `--exit-on-error`; review all warnings and failed objects.
6. Compare baseline table counts, representative complete row fingerprints, schema constraints, RLS, grants, migration history, tenant membership and session references between Development and the **independently restored copy** using a secret-free signed acceptance report. Include Auth identity/factor recoverability and separate Storage **file bytes**, not just Storage metadata. Do not copy sensitive rows into PR comments or test logs. Check credentials and encrypted data can be recovered in the authorised destination; be cautious about side-effecting hooks, emails and webhooks.
7. Only after evidence from steps 1–6 exists, attach a **redacted** receipt recording backup timestamp, origin/destination project identities (no secrets), archive checksum, coverage/exclusions, restoration exit status, table and Auth/Storage verification results, rollback owner and recovery decision. The correct gate status stays **BLOCKED** for any failed or untested essential section. Keep encrypted files off GitHub and away from public runner artefacts.
