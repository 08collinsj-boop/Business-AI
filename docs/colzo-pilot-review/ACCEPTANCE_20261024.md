## Defects fixed in isolated code

1. Proposed grant schema used calendar-day arithmetic, which differed from exactly 336 elapsed hours across the London clock change. The executable regression first failed and now passes with hour-based duration.
2. Membership-only policies allowed expired/revoked pilot reads. The separate staged proposal adds restrictive policies alongside existing tenant policies, using current database grant state rather than stale JWT entitlement claims. Tests switch database roles and reuse the same user identity before and after expiry/revocation.
3. A reserved seat could be consumed by a legacy membership writer. The staged trigger and acceptance transaction now protect capacity at the membership boundary as well as the invitation writer.
4. Controlled grant/invitation/audit operations were absent. A private proposal now implements tested operations without enabling app provisioning. Audit failures do not leave a grant behind; approval evidence and actual database operator identity are recorded separately from the beneficiary owner.
5. Scoped public configuration could advertise the legacy all-features Pilot offer. It now reports approval-only pilot terms and suppresses that offer. The signup UI also refuses self-service registration in scoped mode; existing server-side business-creation/team denials remain unchanged. Direct Supabase Auth registration configuration was not modified and must be reviewed before release.
6. The branch's public-site build did not emit contact/pilot pages. Those pages now build locally, with corrected pilot/demo wording and no instant-activation or payment call to action. No website deployment occurred.

7. Added atomic creation/designation of a new pilot workspace using the existing SQL creator, with tested idempotency and all-or-nothing audit failure recovery.
8. Pilot denials in the browser API function previously appeared as generic permission errors. They now show pilot approval/access and recovery guidance without signing out a valid session or triggering unrelated MFA.

## Database design and its limits

Apply nothing from this report to shared Dev. The four `.STAGED.sql` files are deliberately outside `supabase/migrations` and exist for disposable testing/review only. The original proposal, expiry proposal and provisioning proposal are applied in that order in tests. The workspace proposal then wraps the actual existing `create_business_for_owner` function without changing it.

An existing grant row is the durable pilot designation. Browser and service roles cannot mutate/delete it through these proposals. Unmarked legacy/paid businesses retain their existing access; a revoked/expired pilot row is retained, so it cannot fall back to legacy access. An operator grant is permitted only for an existing verified owner workspace with no paid history. Atomic creation and designation of a new approved workspace is now implemented in the fourth staged proposal. It serialises requests for the verified owner, reuses the existing business/settings/configuration/route creator and adds the grant and two audit events in one transaction. A synthetic injected audit failure left no new business, membership or public route behind. No HTTP writer or real operator connection is enabled.

The restrictive policies do not replace permissive tenant policies or widen existing table grants. The helper checks membership and grant dates with database statement time. All RLS-enabled public tables present during installation with a `business_id` (plus `businesses`) receive the restriction, except membership routing and separately authenticated customer-owned access/complaint tables. Future tables/views and future exposed schemas need explicit review; the installation loop is not automatic protection for subsequently added tables. Service-role API paths still require server-side gates because that role bypasses RLS.

No grant table exists in actual Dev yet, so the security gap remains there. Missing grants cannot be treated as scoped approval by the existing server implementation, but the database cannot identify an unmarked new workspace as a pilot. The staged atomic wrapper closes that window in the tested SQL path. Integration of that wrapper, migration reconciliation and release review remain mandatory.

The audit collector records expiry when invoked; immediate access denial does not depend on a job. No collector/scheduler is enabled. Ownership and identity evidence is an operator attestation requirement, not proof that real business ownership has been verified. Raw invitation tokens are never stored; a future approved sender must generate cryptographically random tokens and hash them before calling the private operation.

## Additional PostgreSQL acceptance

A PostgreSQL 17.11 cluster was created in a separate disposable execution sandbox with TCP disabled and a private 0700 Unix socket directory. No hosted infrastructure, provider activation, paid service, shared Supabase project or real identity was used. The server was stopped after verification.

**25 checks passed across six genuine concurrency scenarios.** The test controller first holds a row lock and confirms at least two independent backends waiting before releasing it. Cases cover identical grant retries, competing final-seat invitations, identical acceptance retries, competing legacy membership inserts, competing workspace requests for one owner, and one verified recipient accepting across two businesses. The final case permitted only one business membership. Five scenarios used eight clients; the cross-business scenario used two.

A PostgreSQL custom-format dump was restored into a separate empty disposable database. Six table counts matched, expired A remained unable to read leads, and authenticated callers still lacked grant-operation privileges. This test retains the synthetic cluster roles; it is not an independent restoration of actual Dev Auth, Storage or configuration. Replay of the runner requires a fresh empty disposable cluster. The initial harness attempt did not establish overlap because a one-shot psql command buffered its lock output; the runner was corrected to hold an interactive transaction and explicitly verify waiting backends before any concurrency pass was claimed.

The new audit regression first demonstrated that `ON CONFLICT DO NOTHING` could hide an expiry event behind a different action using the same request key. The staged collector now validates the existing event and reports an idempotency conflict. Expired access remains denied even when audit collection fails.

Evidence: `POSTGRES_ACCEPTANCE_20261024.json`; runner: `scripts/verify-colzo-pilot-postgres.py`.
